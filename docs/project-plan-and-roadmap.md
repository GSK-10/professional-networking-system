# Project Plan and Implementation Roadmap

A Java and Spring Boot project designed to deepen practical understanding of backend engineering and distributed systems through a professional networking platform. The plan covers product scope, service responsibilities, implementation milestones, and engineering acceptance criteria.

[System architecture](system-architecture.md) · [API specification](api-specification.md) · [Kafka topics and events](kafka-topics-and-events.md) · [Database design](database-design.md)

## 1. Context, goal, and users

Build a focused professional network where a member can create an account, connect with another member, share a short update with an optional image, like an update, and see in-app notifications. The intended users are professionals sharing career updates, colleagues maintaining their network, and members discovering content through their connections. The first release will support a single member role and an API client demonstration; a web interface can follow.

The engineering goal is to apply the practices expected in a backend team: clear service ownership, secure API boundaries, database constraints, predictable failure handling, automated tests, and reproducible operations. The project will deepen understanding of Spring Security/JWT, PostgreSQL transactions, Neo4j graph modeling, and Kafka delivery semantics. Each milestone will produce a working demonstration and evidence for its acceptance criteria.

Core use cases: register/login; view own identity; send/accept/reject a connection request; list first-degree connections; create/read a post; upload one image; like/unlike; read notifications generated by a connection's new post or another user's like. The MVP includes these flows and excludes feed ranking, search, chat, comments, recommendations, email, push, and second-degree discovery.

## 3. Architecture and service responsibilities

See the [system diagram and flows](system-architecture.md). The gateway and discovery server are infrastructure; the other five components implement business capabilities.

| Component | Type | Owns | Main interactions |
| --- | --- | --- | --- |
| API Gateway | Infrastructure | Routing and edge authentication; no business data | Client entry point, JWT verification, trusted identity forwarding |
| Discovery Server | Infrastructure | Service location registry; no business data | Eureka registration and lookup after local API slices work |
| User Service | Business | User accounts, password hashes, JWT issuance, user PostgreSQL schema | Public auth API; `user.created.v1` producer |
| Connections Service | Business | Person projection and connection state in Neo4j | User event consumer; first-degree lookup for Posts |
| Posts Service | Business | Posts, media references, likes in PostgreSQL | Uploader and Connections calls; post event producer |
| Notification Service | Business | In-app notifications in PostgreSQL | Post event consumer; own-recipient read API |
| Uploader Service | Business/supporting | Media upload policy and provider adapter; no MVP database | Internal upload called by Posts; external media provider |

The public base path is `/api/v1`. User Service will own registration, credential verification, and JWT issuance. Keeping account and authentication responsibilities together gives the initial system one clear identity owner.

## 4. Service milestones

### User Service

- **Responsibilities and data:** register users, normalize unique email, hash passwords, verify credentials, issue short-lived JWTs, expose own profile. Own `user.users`; never return password hashes.
- **Endpoints:** `POST /users/auth/signup`, `POST /users/auth/login`, `GET /users/me`, later public profile lookup; full gateway paths in [API contracts](api-specification.md#user-service).
- **Dependencies:** PostgreSQL initially; Kafka when user projection is added. Gateway routes public login/signup and validates tokens on protected calls.
- **Rules:** email uniqueness in database, bounded inputs, generic login failure, canonical user ID in JWT `sub`; publish user creation after committed registration, then improve to outbox.
- **Done when:** two users can register, log in, use a protected own-profile call, and duplicate email or wrong password has a tested outcome.

### API Gateway

- **Responsibilities and data:** route public and protected APIs, validate JWT signature/expiry, strip inbound identity headers, attach validated identity and request ID. Owns no business data.
- **Routes:** User, Connections, Posts, and Notification public paths; Uploader stays internal. See [API contracts](api-specification.md).
- **Dependencies:** User Service JWT verification key or public key, service addresses, later Discovery Server.
- **Rules:** exact public route allowlist, default-deny protected paths, clear token parsing, remove spoofed headers before forwarding, do not expose downstream ports in shared environments.
- **Done when:** anonymous signup/login work through gateway, protected routes reject absent/expired tokens, and a forged `X-User-Id` cannot change the effective user.

### Discovery Server

- **Responsibilities and data:** Eureka registry and health registration; no user data or business endpoints.
- **Dependencies:** services register with it after local direct-address calls are stable. It does not replace health checks or service authorization.
- **Done when:** gateway and one business service resolve a registered name, and a stopped instance is not selected after registry convergence.

### Connections Service

- **Responsibilities and data:** upsert Person projection from `user.created.v1`; own connection pair state in Neo4j; list first-degree IDs and member summaries.
- **Endpoints:** send, list incoming, accept, reject requests; first-degree query in [API contracts](api-specification.md#connections-service).
- **Dependencies:** Neo4j, User event consumer; optionally User lookup to verify targets before projection exists. Posts uses its first-degree lookup synchronously.
- **Rules:** no self-request, duplicate, reverse pending, or already connected pair; recipient only accepts/rejects; unique unordered pair; state transitions transactional. See [data model](database-design.md#connection-state-and-concurrency).
- **Done when:** A requests B, B accepts, both list each other; self, duplicate, reverse, unauthorized accept, and concurrent pair creation cases pass tests.

### Posts Service

- **Responsibilities and data:** persist posts and one optional media reference; create/delete unique likes; list posts by author; own `posts.posts` and `posts.post_likes`.
- **Endpoints:** create/read/list posts, like/unlike in [API contracts](api-specification.md#posts-service).
- **Dependencies:** PostgreSQL; Uploader for images; Connections for recipient IDs; Kafka for post events. Keep creating a text post possible before adding those dependencies.
- **Rules:** actor ID from trusted authentication context, bounded content and image, unique `(post_id,user_id)` like, no event for duplicate like. Media upload failure leaves no post; notification failure must not erase an already saved post.
- **Done when:** two users can create/read posts, add at most one like per user, and an image post stores a valid provider reference with tested failure behavior.

### Notification Service

- **Responsibilities and data:** consume post-created and post-liked, select recipient from event, deduplicate by event ID, persist in-app notifications, expose own-recipient reads/mark-read. Own `notification.notifications`.
- **Endpoints:** list and mark read in [API contracts](api-specification.md#notification-service).
- **Dependencies:** Kafka and PostgreSQL; no synchronous call is required on normal consumption because recipient is in the event.
- **Rules:** never notify a post owner for their own like; unique event IDs; acknowledge only after persistence; no cross-user reads.
- **Done when:** a connection sees a new-post notification, a post owner sees another member's like notification, duplicates create one row, and each member can read only their own notifications.

### Uploader Service

- **Responsibilities and data:** accept an internal image upload, validate size/type, send to one provider, return safe URL or object key. Owns provider integration but no application database in MVP.
- **Endpoint:** internal `POST /uploads/file` multipart; [contract](api-specification.md#uploader-service-and-infrastructure).
- **Dependencies:** media provider credentials supplied through environment or secret manager; Posts calls it synchronously.
- **Rules:** size and MIME allowlist, generated object names, no secret in logs, reject unsupported files, document orphan cleanup when provider upload succeeds but post save fails.
- **Done when:** a valid test image returns a retrievable reference; invalid files fail predictably; no credential is committed.

## 5. Data and event design

User Service's numeric ID is canonical across JWT, PostgreSQL references, Neo4j `Person.userId`, and Kafka. Store only service-owned data; no service reaches into another's schema. Neo4j pair nodes carry `PENDING`, `ACCEPTED`, or `REJECTED` state, with a unique sorted pair key; only accepted pairs appear in first-degree results. [Data model](database-design.md) records full rules and a Cypher query.

The three Kafka topics will be `user.created.v1`, `post.created.v1`, and `post.liked.v1`. User Service produces the first for Connections; Posts produces the other two for Notification. Post creation selects first-degree recipients at creation time and emits one event per recipient. A like targets the post owner. All events carry stable UUID `eventId`; consumer database uniqueness handles redelivery. The event integration milestone will make publication failures visible; the reliability milestone will add an outbox and bounded retries to recover from the database-to-Kafka publication gap. See [payload examples](kafka-topics-and-events.md).

## 6. Key flows and design trade-offs

Registration saves a hashed account, returns the user, and eventually projects a Person node from Kafka; login verifies credentials and issues JWT. A connection request creates one pending unordered pair, then the recipient accepts it and both users appear in first-degree queries. A post with an image calls Uploader, stores the returned reference, asks Connections for first-degree IDs, and emits per-recipient events. A like inserts a unique row and emits one event for the owner. Notification consumes these events and persists a recipient-scoped row. [Sequence diagrams](system-architecture.md#6-registration-and-login) show each flow.

Synchronous calls are used where a request needs an immediate result: upload must return a reference; first-degree lookup chooses recipients. They add latency and failure coupling. Kafka is used for side effects that can appear shortly after the API response, such as graph projection and notifications. That adds eventual consistency and retry/duplication work. Neo4j will model connection relationships and support first-degree traversal, with a path toward mutual-connection queries. An indexed PostgreSQL adjacency table is a viable alternative with lower operational cost; any performance comparison will need a representative dataset and measured queries. Uploader Service will isolate the media provider, chosen according to cost, retention, access control, and deletion requirements.

Build one demonstrable capability at a time. Each phase has prerequisites, implementation tasks, a reviewable result, and acceptance criteria.

| Phase | Prerequisite | Tasks | Demonstrable result | Acceptance criteria |

| 0. Design baseline | Product scope agreed | Review these contracts, decide Java/Spring versions and media provider later, record open choices | GitHub displays plan and diagrams | Links work; planned status is explicit |
| 1. User slice | JDK, build tool, local PostgreSQL | Create User Service, migration, signup/login, password hashing, JWT, validation | Register and log in with API client | Unique email and wrong-password tests; no committed secret |
| 2. Gateway security | Working User Service | Add gateway route, JWT validation, identity header replacement, protected `/me` | Public auth and protected own-profile through one port | Forged header and expired token tests pass |
| 3. Connections local slice | Gateway security; Neo4j | Person nodes, pair constraint/state transitions, request/accept/reject/first-degree API; seed test users initially | Two members connect | State matrix and concurrency integration tests pass |
| 4. Posts text and likes | User identity; PostgreSQL | Posts migration, text create/read/list, unique like/unlike | Member publishes and another likes | Author comes from token; duplicate like prevented by DB |
| 5. Media | Posts working; provider choice | Uploader Service, internal call, image validation, storage reference | Image post can be read with media URL | Invalid/oversize file and provider failure tested |
| 6. Kafka user projection | User and Connections working; local Kafka | Emit `user.created.v1`, upsert Person, reconcile missing projection | Signup creates graph Person asynchronously | Redelivery creates one Person; missing projection can be repaired |
| 7. Kafka notifications | Posts, Connections, Kafka | Publish post events, implement Notification consumer, read API, event deduplication | New post and like produce visible notifications | Only intended recipients see one row per event; consumer retry test passes |
| 8. Reliability | Event flows working | Add outbox to publishers, bounded retry/dead-letter handling, failure observability | Restart after publish failure does not lose event | Demonstrated crash/retry scenario; no duplicate notification |
| 9. Local packaging and CI | Stable services | Docker Compose for app and required stores, migrations, seed/test instructions; GitHub Actions build and test | Fresh clone follows README commands | Clean checkout starts; tests pass in CI |
| 10. Discovery and observability | Multi-service local run | Add Eureka resolution, health/readiness, structured logs, request IDs, basic metrics | Trace a request ID through logs | Services register; health and error rate visible |

For phase 1, running PostgreSQL directly or in a tiny Compose file is enough. Do not add Kafka, Neo4j, a gateway, and every service to the first commit. Keep each phase's demo reproducible before advancing. The full Docker Compose setup belongs after the parts have working local commands, although dependencies can be containerized as each phase needs them.

## 8. MVP and later milestones

**MVP / v1.0:** registration/login, gateway protected calls, connection request lifecycle and first-degree list, text and optional single-image posts, likes, persisted in-app new-post and like notifications, local setup, automated tests, and current project documentation. If time is tight, demonstrate text posts and connections first, then complete image and notifications before calling v1.0 done.

**v1.1:** outbox, stronger retry/dead-letter handling, projection reconciliation, and pagination polish; basic notification deduplication is already part of MVP. **v1.2:** profile editing, connection request notifications, remove/withdraw connection, media deletion and cleanup. **v1.3:** simple chronological feed, privacy controls, search or second-degree suggestions after use cases justify them. **Optional operations:** metrics dashboard and tracing, then deployment work if the project is already maintainable locally. Kubernetes, Helm, ELK, Zipkin, and a frontend are later options, not MVP prerequisites.

Optional improvements include token rotation or asymmetric signing, rate limiting, media object keys and signed delivery URLs, contract tests, and retention policies. Avoid a separate Auth Service, config server, service mesh, multiple media providers, recommendation engine, chat, live notifications, and complex feed ranking before the basic flows are tested.

## 9. Local development, tests, CI, and visibility

Local setup documentation will cover the required JDK, Docker, ports, environment variables, migrations, startup order, and example API calls. Commit `.env.example` with names only and keep real secrets local. Use one PostgreSQL instance with service-owned schemas, one Neo4j instance, and one Kafka broker for development; Compose health checks should express readiness. Use service DNS inside Compose. A mock or local media adapter may support tests; real provider calls need isolated credentials. Keep signing keys, database passwords, and provider credentials outside version control; document their environment variable names and rotation process.

Test business rules at the service layer and use database integration tests for email uniqueness, likes, connection pair concurrency, and notification deduplication. Add gateway tests for token expiry, spoofed headers, and public-route allowlist; contract tests for Feign request/response shapes; one end-to-end happy path. Use Testcontainers where practical for PostgreSQL, Neo4j, and Kafka, but keep the normal unit suite quick. Basic CI should compile, run unit and selected integration tests, and check Markdown links/diagrams. Add Docker image builds only after services exist.

Start observability with Actuator health/readiness, structured JSON logs, request IDs propagated across HTTP, and Micrometer HTTP/error metrics. Track Kafka consumer failures and outbox backlog when those features exist. A Prometheus/Grafana dashboard can follow; distributed tracing and central log stacks should answer a concrete debugging need before they are added.

## 14. Open decisions before coding each affected phase

1. Choose Java, Spring Boot, Spring Cloud, and library versions as a tested compatibility set when scaffolding begins.
2. Decide whether `ConnectionPair` IDs remain canonical pair keys in public API or become opaque IDs.
3. Select a media provider and define image size/type, public versus signed URL, deletion, and cost limits.
4. Set JWT lifetime, symmetric versus asymmetric key management, and whether downstream services independently validate JWTs.
5. Decide the exact post creation behavior when Connections lookup is unavailable, and implement it consistently with event recovery.
6. Set like/unlike repeat-call status policy and whether image-only posts are allowed.
